# Orbium v0.1.0 scope

This document is the scope boundary for the first release.

## Must ship

### Foundation

- Laravel 13 / PHP 8.4 application
- React 19 + TypeScript + Inertia
- Vite 8
- Tailwind CSS 4
- PostgreSQL
- authenticated user accounts
- user data isolation
- Docker self-host baseline
- automated formatting/lint/type/build/test commands

### Workspaces and hierarchy

- multiple workspaces per user
- create/rename/delete workspaces
- folder/document/database nodes
- parent-child relations
- containment validation
- move/reorder nodes
- no hierarchy cycles
- breadcrumbs
- trash/soft-delete behavior for user content
- workspace switcher

### Documents

- Tiptap/ProseMirror editor
- Notion-style block UX
- Markdown shortcuts
- slash command menu
- block handles
- selection toolbar
- autosave
- code blocks with syntax highlighting
- programming-language label and icon
- Mermaid
- math
- tables
- images
- file attachments
- mentions to folders/documents/databases
- mention picker
- mention index/backlink-ready data model
- clean reading/editing surface
- `Ctrl + F` current-document search

### Databases

- database node/container
- database child documents
- properties:
  - Text
  - Number
  - Select
  - Multi-select
  - Checkbox
  - Date
  - URL
  - Email
  - Files
  - Mention
- built-in title
- inline property editing
- property create/edit/reorder/delete
- property defaults where useful and safe
- Table view
- Gallery view
- Orbit view
- simple filters
- multiple sorts
- per-view settings
- same underlying documents across all views

### Navigation

- Search Master (`Ctrl + Space`)
- global commands
- current-workspace search
- PostgreSQL FTS + `pg_trgm`
- native workspace selector in the top bar
- workspace and folder explorer
- tabs
- tab persistence
- per-tab navigation history
- reveal in Orbit
- direct search jump

### 3D Orbit

- React Three Fiber / Three.js / Drei
- central current node
- direct children only
- deterministic layout
- folder/document/database visual differentiation by form/material
- minimal continuous orbital drift
- hover/select/open interactions
- GSAP navigation transitions
- breadcrumbs remain deterministic escape route
- reduced-motion support
- database Orbit uses same spatial engine
- no mention edges

### Portability

- one portable Orbium archive
- independent archive format version
- streaming NDJSON table data
- binary file inclusion
- SHA-256 checksums
- exact archive-entry validation
- safe ZIP path validation
- explicit supported format registry
- backward adapters
- reject unsupported future formats
- schema/row validation
- semantic relationship validation
- consistent export snapshot
- verified generated export
- upload + validate + preview before restore
- fresh restore path
- existing-account replacement
- safety export before destructive replacement
- write lock during restore
- old-ID → new-ID mapping
- embedded editor-content ID remapping
- transactional database restore
- staged binary restoration
- post-restore verification
- repeated restore must not duplicate the logical graph

### Settings/onboarding

- Appearance
- Workspace
- Editor
- Storage information
- Portability
- Account
- short onboarding
- first workspace creation
- restore from archive during onboarding
- empty states
- clear server/error states

## Explicitly not in v0.1.0

See `docs/15-deferred-features.md` for detail.

The following are deferred:

- AI generation/editing/chat
- 2D global mention graph
- collaboration / multi-user shared workspaces
- comments
- real-time collaborative editing
- public sharing
- cloud hosted paid service
- offline-first/local-first sync
- mobile-first redesign
- database Board/List/Calendar/Timeline views
- Formula/Rollup/Person/Progress/Location properties
- required database properties
- database templates
- arbitrary relation properties
- 3D mention links
- custom user CSS/themes
- version history
- Redis
- Meilisearch/Elasticsearch
- WebSockets
- MinIO/S3 as required infrastructure
- physics-driven orbital layout
- plugin system

## Scope decision rule

If a requested implementation detail is not necessary to satisfy a must-ship item, prefer not to add it to v0.1.0.

A future-friendly schema is good. Shipping future functionality early is not.
